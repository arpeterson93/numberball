## Task 1 — Port the xlsx trajectory physics into the LA/EV → distance/hang-time step

Today, `flightParams` computes `LA`, `EV`, and `D` as **three independently interpolated numbers** from the same per-result Statcast percentile ranges in `result_diff_bands.csv` — `D = depthMin + q*(depthMax-depthMin)`, with no physical relationship to `LA`/`EV` at all. Replace `D`'s derivation (and the hang-time formula, currently a drag-free vacuum `2*v*sin(θ)/g` — see finding F10) with a real trajectory integration that takes `LA` and `EV` (which continue to come from the existing per-result Statcast percentile interpolation — that part is not changing) and derives distance, hang time, landing point, and the ball's velocity at ground contact, jointly and consistently, the way the workbook does.

**Physics reference, extracted directly from `BattedBallTrajectory-1` (cell coordinates given for verification, not for literal transcription):**

- Inputs: exit speed `v0` (mph, cell B6), launch angle `θ` (deg, B7), direction `φ` (deg, B8), batter hand (B9). Everything else below is either a derived quantity or an atmospheric default that can stay fixed (temp 75°F, elevation 0ft, wind 0mph, humidity 50%, pressure 29.92 inHg — MLN plays aren't tied to real stadiums, so there's no per-park variation to source unless you decide there should be; the `Elevations` tab has real per-stadium data if that's ever wanted, out of scope here).
- Velocity components (ft/s, `v0` converted to ft/s via `×1.467`): `v0x = v0·cos(θ)·sin(φ)`, `v0y = v0·cos(θ)·cos(φ)`, `v0z = v0·sin(θ)`.
- **Spin is derived automatically, not supplied** (the workbook's `BattedBallTrajectory-2` tab takes manual spin instead — not needed here): `backspin = -763 + 120·θ + 21·φ·sign`, `sidespin = -sign·849 - 94·φ`, where `sign = +1` for R-handed, `-1` for L-handed. `spin = sqrt(backspin² + sidespin²)`.
- Drag coefficient: `Cd = cd0 + cdspin·(spin_perp/1000)·decay(t)`, with `cd0 = 0.3008`, `cdspin = 0.0292` (both already quoted correctly in `physics-model-overview-for-redesign.md`). `spin_perp` is the component of spin perpendicular to the velocity vector; `decay(t)` is a slow exponential spin-decay term (time constant effectively very long — `tau = 10000s` in the workbook — so treat spin as near-constant over a single play's flight unless closer fidelity is wanted).
- Lift coefficient (Magnus/backspin lift): `Cl = cl2·S / (cl0 + cl1·S)`, with `cl0 = 0.583`, `cl1 = 2.333`, `cl2 = 1.12`, where `S` is the spin factor — the ratio of the ball's transverse (Magnus-relevant) rotational speed to its speed through the air.
- Per-axis acceleration = drag term (`∝ -Cd·|v_rel|·v_rel`, `v_rel` = velocity relative to wind, wind is 0 here so `v_rel = v`) + Magnus/lift term (`∝ (Cl/ω)·|v_rel|·(ω × v_rel)`) + gravity (`-32.174 ft/s²` on the z-axis only). Both drag and lift terms scale by a shared constant `const = 0.07182·ρ·(5.125/mass)·(circumference/9.125)²` folding in ball mass/size and air density `ρ` (itself a function of temp/elevation/humidity/pressure — fixed defaults per above).
- **Integration**: simple explicit Euler step, `dt = 0.01s` in the workbook (position += velocity·dt + ½·accel·dt², velocity += accel·dt), run forward until `z` crosses 0. The final landing point/hang time/distance are then **linearly interpolated between the last two sampled rows** to the exact `z=0` crossing (workbook rows ~23–29). A browser implementation does not need to match `dt=0.01` exactly or use Euler specifically — decide in the plan whether a coarser step or a more stable integrator (e.g. RK4) is worth it for a client-side per-play computation — but it must integrate the same underlying drag+lift+gravity ODE with the same coefficients, and it must produce the ball's **velocity components at the moment of ground contact** (not just position), since Task 3 needs them.
- **Angle-convention mapping (must be solved explicitly, not assumed):** the workbook's `direction φ` is 0°=straight at 2nd base, +45°=toward the 1B line, −45°=toward the 3B line, with hand folded into the *spin* formulas rather than the direction itself. The app's own `HZ` angle (`docs/js/app.js`, `HZ_FIELDER_BY_ANGLE` neighborhood) is a 0–90° scale with 45°=straightaway and hand already folded into the angle formula itself (`angle = hand==='L' ? 45 - frac*40 : 45 + frac*40`). These are two different conventions for encoding the same physical direction — the mapping is approximately `φ = HZ_angle − 45`, but this must be pinned down, not assumed, because the two systems fold "hand" into different parts of the formula (the app into the angle, the workbook into the spin), so handedness can end up double-counted or cancelled. Resolve it with a throwaway probe script that feeds known cases through both conventions (does `HZ=45` map to dead center; do `HZ=5`/`HZ=85` map to the two foul lines; does a L vs. R batter at the same `HZ` produce the mirror-image `φ` you'd expect) and reports the actual sign behavior. Put the verified mapping — with the exact hand-sign resolution — directly in the plan; only if the probe is genuinely inconclusive should this drop to the open-questions list.

**What this changes downstream:** `D` (distance) and `hangMs` both become outputs of this integration instead of independent lookups/formulas — this directly resolves finding **F10** (vacuum-physics hang time contradicting Statcast depth). The **inputs** `laMin`/`laIdeal`/`laMax`/`evMin`/`evMax` (still real Statcast percentiles from `result_diff_bands.csv`, still interpolated by `q` exactly as today) are unchanged. Decide explicitly in the plan whether `depthMin`/`depthMax` still get used at all post-port (e.g. as a sanity clamp/fallback, or removed entirely since distance is now derived) — this affects `compute_flight_ranges.py` and the CSV schema, and should be called out as a migration step.

One existing, deliberate exception to check against this port: `grounder`/`infield_single`/`bunt`-family results currently use **hand-tuned real-infield-depth ranges**, not Statcast percentiles, for `depthMin`/`depthMax` (because `hit_distance_sc` measures first-bounce point, not fielded depth, for ground balls — see the source doc's Stage 2 section and finding **F2**, which found the *same* first-bounce-as-landing-point problem still present, uncorrected, in `1B`/`2B`). Once distance comes from a real trajectory integration off `LA`/`EV`, decide whether this special-cased override is still needed at all, or whether the physics naturally produces a short/shallow first-touch point for a grounder-shaped `LA` without needing a hand-tuned depth table — and whether that also finally gives `1B`/`2B` a principled fix for F2 instead of the "deliberately not applied" gap the source doc flags.

## Task 3 — Rollout/bounce physics after ground contact

The xlsx model only integrates to the *first* `z=0` crossing — it has no bounce/roll model at all (confirmed: `physics-model-overview-for-redesign.md` notes it extrapolates "to field level," and inspection of the workbook confirms the landing-point rows stop at first ground contact). Today's rollout (`groundBallRolloutFt`, `rolloutFraction`) is a heuristic bolted on afterward — `rolloutFraction(ev, la) * (depth - flight.distance)`, scaling toward whatever depth the fielder-assignment step decided on, using a **global, non-per-result** EV/LA normalization (`ROLLOUT_EV_LOW/HIGH`, `ROLLOUT_LA_LOW/HIGH`) that finding **F4** shows is incoherent against the now-per-result rest of the pipeline (constant rollout for anything but `GO`-shaped results; zero rollout for bunts only because `ROLLOUT_EV_LOW` happens to sit above bunt EV — finding **F8**, a "works by luck" case).

Design a physics-derived replacement: use the ball's actual horizontal and vertical velocity components **at the moment of ground contact** (an output of Task 1's integration) to drive a bounce/friction model — vertical coefficient of restitution for bounce height/decay, horizontal friction/rolling deceleration for how far and how fast it continues — rather than a heuristic fraction of a fielder-depth gap. This is exactly the fix Alex's own note in the source doc calls for: *"a physics-derived distance/hang-time pair should get a physics-derived rollout too (e.g. residual ground speed at landing, from the same trajectory calculation), not a separately-patched heuristic bolted on afterward."*

Critically, tie this to Task 4 rather than solving it standalone: since Task 4 determines *which fielder* and *at what depth* the ball is fielded, Task 3's job is not "how far does an unconstrained ball roll to a stop" — it's "given the ball's real ground-contact speed/direction, how long does it take to reach the depth Task 4 says it's fielded at." Design these two as one coherent mechanism, not two patches that happen to agree. Keep the archetype gate: fully-airborne fly balls/line drives that are caught in the air never enter this path at all (today's `CAUGHT_IN_AIR` early return / `GROUND_ARCHETYPES` gate — preserve that boundary).

## Task 4 — Infielder interception: solve depth from the known result, not a lookup table

Restate the mission constraint concretely for this task: for a ground ball that the result table already says is fielded cleanly (an out via a specific position, or a hit past a specific position), we already know **who fields it** (from `import_BRC.csv`'s `DefaultPosition`/`ExcludedPositions` for this exact `(result, obc, outs)` situation when present, otherwise from the HZ spray angle via `HZ_FIELDER_BY_ANGLE`) before any physics runs. What we don't know yet is **at what depth** that specific fielder actually intercepts this specific ball, given their real fielding depth and this play's specific trajectory.

Today's mechanism is three different, disagreeing patches layered on top of each other — this is the redesign's second big target per the source doc, and three of the review's findings are direct evidence of the damage this causes:

- **F1** — `applyPositionOverride` rewrites `flight.angle` to an arbitrary real-number angle derived from `atan2` against a fielder anchor, which then misses the `HZ_FIELDER_BY_ANGLE` lookup's discrete 11-value lattice in 4 of 5 cases tested. `groundBallRolloutFt` repeats the HZ lookup independently, misses, and silently falls back to the old flat-constant rollout with no depth cap at all — the ball can roll *past* the very fielder the override existed to snap it to (concrete case: `DP31`, ball rolls 17–22ft behind the 3B anchor).
- **F3** — `flight.fielder` (set by `nearestFielder`, plain nearest-anchor-by-proximity) and the HZ-assigned fielder disagree on 39% of the grounder (q, angle) grid — every shallow grounder resolves to `P` by proximity regardless of actual direction. `applyPositionOverride`'s exclusion-position check uses `flight.fielder` (the proximity answer), not the HZ answer, so exclusions can fire against the wrong position.
- **F5** — `FIELDER_ANCHORS_FT` (used for the position-override snap and `nearestFielder`) and `INFIELDER_DEPTH_FT` (used for the cap/rollout depth) are two independently hand-placed sources of truth for the same 5 infield positions, disagreeing by up to 5.6ft.

Design a single, unified mechanism that replaces `HZ_FIELDER_BY_ANGLE` + `INFIELDER_DEPTH_FT` + `applyGroundBallFielderDepth` + `groundBallRolloutFt`'s depth-lookup + `applyPositionOverride` + `nearestFielder`'s role for grounders, along these lines:

1. Determine the fielding position for this play from `import_BRC.csv`'s per-situation `DefaultPosition`/`ExcludedPositions` when present, else from the HZ angle bucket — this decision precedes and is independent of any physics.
2. If the HZ-derived fielder is inconsistent with what `import_BRC` requires for this situation, **override the HZ angle itself** to the minimum angle in `HZ_FIELDER_BY_ANGLE` that already maps to the required position (e.g. 3B's angles are `{5, 13}` → override to `5`), per the proposal already written up in the source doc's "A cleaner way to think about HZ-to-fielder validity" section — **the original `LA`/`EV` must not change** when this fires, only direction.
3. Using the (possibly corrected) HZ angle and a single authoritative real-world depth for that position (resolve F5 by picking one source of truth — decide which, or derive both anchor and depth from the same underlying number), compute where along the ball's **real physical path** (Task 1's flight to first ground contact, plus Task 3's bounce/roll continuation) that fielder's depth is actually crossed, and derive fielding time from that same physics rather than snapping to a static table constant.
4. `flight.fielder` should end up set consistently with this same determination in every case, not just on the capping path (F3's fix) — audit every place that currently reads `flight.fielder` or independently re-derives a fielder via `nearestFielder` for a grounder to make sure there's exactly one source of truth after this change, not two.

**Outfield scope decision, flagged explicitly for you to resolve, not guess:** the source doc notes outfield fielder assignment (`nearestFielder` against all 9 `FIELDER_ANCHORS_FT`) has no depth-reconciliation step analogous to the infield one at all today — it's unclear whether outfield distances ever get corrected against real fielder positioning. Decide and justify whether Task 4's unified mechanism should extend to outfielders too, or whether infield-only is the right scope for this pass (outfield "fielded cleanly" plays are mostly caught in the air, where this whole depth-interception problem may not apply the same way — but flag it, don't silently assume).
