## Project context

Numberball has two separate faces that share a Supabase backend but are otherwise independent:

1. **The Streamlit scouting app** (`pages/1_Games.py`, `pages/2_Scouting.py`, etc.) — a live tool, queries Supabase directly per request.
2. **"Gameday"** (`docs/` — static HTML/CSS/JS, deployed via GitHub Pages) — a slideshow/replay site over MLN's current season only. This is what this task is about.

Gameday's data pipeline: `key_moments_build.py`'s `build(sheet_id)` reads live from a Google Sheet (`MLN_SHEET_ID` constant, currently season 13), computes win probability/leverage/tags for every play, and writes static JSON — `docs/data/{key_moments,players,meta,plays_NN}.json` (one `plays_NN.json` per session number within the season). The site's own JS (`docs/js/app.js`) fetches these fixed filenames directly (`fetch('data/plays_0'+s+'.json')` for `s` in a hardcoded session list) and does all filtering/rendering client-side. There's already a **Session** `<select>` in the UI (`docs/index.html:31`, `id="session-select"`, populated/wired in `docs/js/app.js` ~lines 6880-7044) — the natural sibling to model a **Season** selector on, but there is currently no season concept in the site at all; it only ever knows about one season's worth of sessions.

The live build runs on a recurring cadence (roughly every 30 min, per existing tooling) since the current season's sheet is still being actively played and scored. **Old seasons don't change** — this asymmetry matters for the plan (a historical season's JSON can be built once and never touched again, unlike the current season's).

## The ask

Alex wants historical MLN seasons (prior to the current one) browsable on the Gameday site — same session/game/play drill-down that exists today, just also reachable for past seasons. His own words, verbatim, on the parts he's unsure about:

> I'm not sure UI-wise where the season toggle should go. And I'm worried about bloat with bringing in 80k-ish plays. While at the same time, being able to filter across all of them would be amazing. So there's some combo of like having access to all the data while also not maybe always trying to access all of it if the site will just get bogged down.

Two things to design for simultaneously, in tension:
- **Default browsing should stay cheap.** Nobody should download 12 seasons' worth of plays to look at one game from the current one.
- **Cross-season filtering should still be possible.** Whatever "filter across all of them" ends up meaning concretely (see open questions), it can't require every visitor to pull the full historical corpus client-side just in case they use it.

## Second ask: deep-linkable game URLs (a separate MLN-reference site links here)

Alex also wants an *external* site — a separate "MLN-reference" site he runs/uses that publishes box scores — to be able to link a box score directly to that same game's replay on Gameday. Concretely: a URL containing a game id that, when opened, lands on the Gameday site and launches that game's slideshow automatically, with no manual searching/clicking required on the visitor's part. This is a distinct feature from historical-season browsing, but shares the same underlying data-loading problem, so plan them together — a game link into an old season needs exactly the same "load just this one season's data on demand" path the historical-seasons work above already has to build.

What already exists to build on:
- The site already has an internal "jump to a specific play" flow: `docs/index.html`/`docs/js/app.js` renders buttons carrying `data-jump-game`/`data-jump-session`/`data-jump-num` attributes, a click handler (`docs/js/app.js` ~line 7328) reads them and calls `openReplayAtPlay(gameCode, session, playNum, btn)` (~line 6770), which lazy-loads that game's plays (`loadGameReplay`), builds the slideshow, opens the replay modal, and jumps straight to the matching play. This is a *button-click*-only flow today — there is currently **no code anywhere that reads the page's URL** (`window.location.search`/`.hash`) on load. `git grep` for `URLSearchParams`/`location.hash`/`pushState` in `docs/js/app.js` turns up nothing. Deep-linking is a net-new capability, not a fix to something broken.
- `openReplayAtPlay` takes a **session number**, not a season — sessions restart their numbering each season (same fact from the historical-seasons section above), so a bare session number is ambiguous across seasons on its own.
- Promising lead worth confirming, not yet fully verified: `game_code` appears to already encode more than just "which game" — `utils.split_play_num`'s own docstring pins the contract `130317034 -> (130317, 34)` (game_code, in-game sequence), and every real `game_code` observed this session (`130119`, `130218`, `130321`, `130417`, `130419`, ...) starts with `13`, matching the current season constant (`_CURRENT_MLN_SEASON = 13` in `sync_plays.py`). That strongly suggests `game_code` is structured as `{season:2d}{session:2d}{game_in_session:2d}` — if confirmed, **`game_code` alone is enough to identify season + session + game**, with no separate parameters needed at all. Verify this against real historical game codes from more than one season before relying on it (only season-13 codes were available to check locally) — if it holds, it substantially simplifies both this feature and the historical-seasons work, since a single game_code is then a complete, self-describing key into whichever season's data file needs to be lazy-loaded.

## Open questions to raise back to Alex (don't silently resolve these)

1. **Source of truth for historical data** — Supabase (already populated, `season`-scoped, no external dependency) vs. the `.xlsx` archive vs. a Google Sheet Alex still needs to locate/share the ID for. If Supabase, does its schema/data already match what `key_moments_build.py` expects from a live sheet closely enough to reuse the same build logic, or does that logic need a second code path?
2. **What does "filter across all of them" concretely mean?** A few very different features hide under that one sentence — worth enumerating explicitly and asking Alex which (possibly several) he means:
   - Search/filter *within* one season at a time, just make it easy to switch which season you're looking at (cheapest — this is closest to what the Session dropdown already does).
   - A cross-season leaderboard/stat search (e.g. "show me every play matching X across all 13 seasons") — this needs either a server-side query (Supabase, live) or a prebuilt aggregate index, not full per-play JSON for every season loaded client-side.
   - Full play-by-play replay browsing of an old season, same fidelity as the current season's slideshow, just for a season picked from a dropdown — this is "lazy-load one season's full JSON," cheap per visit but means N seasons × full build pipeline at build time.
   These have very different bloat/complexity profiles — the plan should propose an architecture, but the *scope* (which of these Alex actually wants) is his call.
3. **UI placement for the season toggle** — Alex explicitly said he doesn't know. Propose 2-3 concrete options (e.g. sibling dropdown next to Session; a season selector that gates/repopulates the Session dropdown since sessions aren't unique across seasons; a separate "Browse History" entry point distinct from the live/current-season view) with tradeoffs, rather than picking one silently.
4. **Build cadence implications** — historical seasons never change, so their JSON (or whatever the chosen artifact is) only needs to be built once, ever, not on the current season's ~30-minute rebuild cycle. Does the build script need a `--season`/one-time-backfill mode distinct from its normal incremental run, and where do historical build outputs live (same `docs/data/` tree with season-suffixed filenames? a separate directory?) so the live rebuild never has to touch or re-derive them?
5. **Win probability / leverage / tagging** — `key_moments_build.py` computes these per play using situational frequency tables that were themselves derived from MLN's history (see `mc-win-probability-leverage-plan.md`). Confirm whether those tables' own training data should now include historical seasons once they're playable on the site (a completeness question) or whether that's explicitly out of scope for this task.
6. **URL format for game links** — query string (`?game=130419`) vs. hash (`#game=130419`). For a single-page static site with no server-side routing either works; hash avoids the (here, irrelevant) concern of a query string hitting a server, query string is the more conventional/expected shareable-link shape. Recommend one with reasoning rather than picking silently.
7. **Play-level granularity** — the ask as stated is game-level ("launch the corresponding game's slideshow"), but the existing internal mechanism (`openReplayAtPlay`) already supports jumping to a specific play for free. Worth exposing as an optional URL param (e.g. `?game=130419&play=19`) for a future "link to this exact moment" use case, or explicitly out of scope for this pass? Alex's call.
8. **How does the external MLN-reference site obtain a correct `game_code` to link to?** If it's a completely separate system Alex doesn't control the internals of, it needs *some* way to know Numberball's own `game_code` per game it wants to link — confirm whether that mapping already exists somewhere (a shared sheet column, a lookup Alex maintains by hand, an API) or whether this task needs to produce one (e.g. a small public lookup/search endpoint or page).
