**Decision 2 - the deterministic pitch/swing -> flight-parameters math.** This is the core of the feature; reproduce it exactly, it has been hand-verified against real rows pulled from Supabase.

Given integers `pitch`, `swing` (1-1000) and the play's existing `diff`:

```
first_two(v) = floor((v-1)/10)          # 0..99
ones(v)      = (v-1) mod 10             # 0..9
signed_circ(a, b, mod):                 # generalizes utils.circular_signed_delta to arbitrary modulus
    d = b - a
    if d > mod/2: d -= mod
    elif d < -mod/2: d += mod
    return d

dLA    = signed_circ(first_two(pitch), first_two(swing), 100)   # -50..50
bucket = signed_circ(ones(pitch), ones(swing), 10)              # -5..5 (+5 and -5 are the same wheel position)
```

- **Launch angle** (uses `dLA`, i.e. the *first two digits*): `p_launch = (1 - dLA/50) / 2` (0..1). Positive `dLA` means pitch's value had to increase to reach swing's - read as "swing landed above pitch on the wheel, i.e. hit down on the ball" - maps toward the **low** end of the result's launch-angle band; negative `dLA` maps toward the **high** end. `LA = LA_min + p_launch * (LA_max - LA_min)`.
  - **Deliberately NOT decorrelated from `diff`/contact quality** - unlike horizontal (next), a real "barrel" genuinely does cluster near an optimal launch angle, so great contact producing a consistent, narrow launch-angle result is realistic, not a bug. Do not attempt to fix or flag this.
- **Horizontal angle** (uses `bucket`, i.e. the *last single digit*, hand-aware): `frac = bucket/5` (-1..1). RHH: `angle = 45 + frac*40` (5°-85°, negative frac = "early"/pulled = toward the 3B-line/low-angle side). LHH: `angle = 45 - frac*40` (mirrored - pull is toward the 1B line for a lefty). 0° = down the 3B line, 90° = down the 1B line, 45° = dead center.
  - This specific design (last single digit, not the whole diff or the last two digits) exists **because** the naive versions produced a real, verified bug: for any result whose typical `diff` stays under half the modulus used (true of every last-two-digit or full-value approach for low-diff results like HR), the digit-delta becomes numerically forced to near-zero, clustering nearly every home run at ~45° regardless of the actual pitch/swing pair. The mod-10 version fixes this because a low-diff category's typical diff range (e.g. HR's 0-21) spans multiple full wraps of a 10-wide wheel, which scrambles/decorrelates the result. **Do not "improve" this by widening the modulus or dropping swing from the formula - both were tried and explicitly rejected by Alex.**
  - Batter hand is required for this axis. This is why Decision 6 (threading `hand` into the JSON) is not optional infrastructure - the horizontal axis silently degrades to nonsense without it.
- **Exit velocity**: `q = 1 - clip((diff - band_lo)/(band_hi - band_lo), 0, 1)`, where `band_lo`/`band_hi` are **that specific `result` value's own** diff 10th/90th percentile (Decision 3's diff-band table - NOT the archetype-pooled band). `EV = EV_min + q * (EV_max - EV_min)` using the result's archetype EV band (Decision 3).
- **Distance**: `D = depth_min + q * (depth_max - depth_min)` - same `q` as exit velocity, reused deliberately (harder/cleaner contact both reads faster and carries farther).
- **Hang time / roll, branched on `LA`**: if `LA` is at or above roughly 3-5 degrees, it's airborne - `T = 2 * (EV_mph * 1.4667) * sin(LA in radians) / 32.2` seconds (real drag-free projectile time-of-flight; this is fine for *timing* even though it would be wildly wrong for *distance* - see the note below). Below that threshold it's a grounder: no parabola, a short ground-level roll to `D`, not a physics formula (exact roll duration is an animation-feel judgment call, not specified further here).
  - **Why distance is not computed from EV/LA via the standard ballistic range formula**: verified by hand that it wildly overshoots real distances (a 109.9mph/30° drag-free calculation comes out near 700ft against a real ~400ft expectation) because real air drag removes roughly half the naive range. Distance must come from the category depth band (above), never from `EV^2 * sin(2*LA) / g`.
- **Landing point** (field-plane Cartesian, home plate at the origin, +y = depth into the outfield, 45 degrees = dead center): `offset = angle - 45`; `x = D * sin(offset in radians)`; `y = D * cos(offset in radians)`.
- **Fielder**: nearest of 9 fixed, generic position anchor points to `(x, y)`. No names, no per-play defensive alignment (Decision on Lineups above).
- **Throw sequencing, v1 scope**: at most **one** throw, to whichever base the out actually occurred at, derived from the **existing** `deriveRunnerMoves`/`obc_before`/`obc_after` logic already used for the runner-token animation - do not build new out-attribution logic. Double plays get exactly one throw in v1, not the full two-throw choreography (explicitly deferred, not an oversight).
