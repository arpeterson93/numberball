# MLN Gameday ball-flight model: how it works today, and why it keeps needing patches

## Purpose of this document

This describes the *current* system faithfully — including the patches layered on top of patches — so a fresh model can redraft the implementation with the whole picture in view, rather than incrementally fixing the next symptom. It is not a review of whether today's individual fixes were correct (several were verified against real MLB Statcast data this session); it's a design-level account of why the overall shape of the system keeps producing bugs of the same family. **The ask at the end is to redesign, not just patch further.** Alex's own annotations are marked **[Alex's note]** throughout so the redesign can tell "how it works today" apart from "what Alex already thinks is wrong with it."

Everything here is grounded in the actual code as of today, in `docs/js/app.js` (the animation/physics implementation), `result_diff_bands.csv` (the data), `compute_flight_ranges.py` (data generation from real MLB Statcast via `pybaseball`), `compute_result_diff_bands.py` (a second, independent data generator for a different column set), and `ball_flight_test.py` (the Playwright-based pure-function test suite).

## Mission context — what this game actually is, and what the physics layer is for

**[Alex's note]** This is worth internalizing before redesigning anything: the underlying Discord league game (MLN) has *never* had a physical component. The entire game mechanic is: roll two numbers (pitch, swing), look up which result that pitch/swing pair corresponds to in a table, and track the game from that result. There is no batted-ball speed, angle, or direction anywhere in the actual rules — a "1B" is just a `1B`, with zero specifics about how hard or where it was hit.

Everything described in this document — LA, EV, distance, spray direction, which fielder touches the ball — is a layer *invented on top of* that table lookup, built by cleverly re-reading the same pitch/swing numbers that already determined the result as if they were Statcast-style batted-ball inputs. The goal is to render a plausible, internally consistent physical *story* for a result that has already been decided, purely for the visualization on the SVG diamond.

This means one constraint outranks every other design decision in a redesign: **the physics must never contradict or reinterpret the result the table already produced.** A `1B` must always visually resolve as a single, a `DP` as a double play, etc. — the physics engine's job is to make that already-fixed outcome *look* like a real, coherent batted ball, not to have any say in what actually happened. Any redesign is free to change how LA/EV/distance/spray/fielder get computed, but the result itself is always upstream and immovable.

## The three things this document walks through, in the order the code actually computes them

1. How a raw **pitch/swing** number pair becomes a **result** and a **contact-quality signal** (nothing physical yet — this stage is pure game mechanic).
2. How that contact-quality signal becomes **launch angle, exit velocity, and distance** (this is where "physics," or at least real MLB Statcast data, enters).
3. How the ball's landing spot gets reconciled with **which fielder is actually standing there**, especially for ground balls (this is where most of today's bugs lived).

---

## Stage 1: pitch/swing -> result, contact quality, and spray direction

Every plate appearance has a `pitch` and a `swing` value, each an integer 1-1000 (a circular wheel — 1000 and 1 are adjacent). Two independent things get derived from this one pair:

**a) `diff`** — the full circular distance between pitch and swing (`utils.circular_diff`, all three digits). This is computed once, server-side, and shipped with the play. Every MLN result code (`GO`, `HR`, `1B`, `DP`, ...) has its own `[band_lo, band_hi]` range of `diff` values that produce it (`result_diff_bands.csv`, generated by `compute_result_diff_bands.py` from MLN's own real play history in Supabase — this is a completely separate data source and generation script from the Statcast-derived columns described in Stage 2). Given a play's actual `diff` and its result's band, `q = 1 - clamp((diff - lo) / (hi - lo), 0, 1)` — `q=1` means "diff sits at the best-timed end of this result's own range," `q=0` means the worst-timed end still capable of producing this result.

**b) HZ (spray direction)** — computed from a *completely different* slice of the same two numbers: `lastDigit(pitch)` and `lastDigit(swing)` (literally the last decimal digit, 1000→0), fed through the same circular-distance machinery on a mod-10 wheel. That gives a bucket in -5..+5, which maps linearly to a field angle: `angle = hand==='L' ? 45 - frac*40 : 45 + frac*40` where `frac = bucket/5`. This produces exactly 11 possible angles (5° through 85°, in 8° steps), **the same 11 angles and the same formula for every single result code** — a routine comebacker and a pulled home run both spray across the identical 5-85° window, mirrored by batter handedness.

Nothing about spray direction is aware of what result actually occurred, or of real MLB spray tendencies for that result. (We know from checking real 2025 Statcast data that this doesn't match reality: real triples in that season showed a 120/208/337 LF/CF/RF split by `hit_location`, nowhere close to symmetric — a real per-result spray idea was scoped in a separate conversation but never implemented.)

## Stage 2: contact quality -> launch angle, exit velocity, distance

This is `flightParams(play, tables)` in `docs/js/app.js`. `tables.bands[result]` (from `result_diff_bands.csv`, loaded via `key_moments_build.py`'s `_flight_meta()`) carries, per result: `lo`/`hi` (the diff band from Stage 1a), `archetype` (a plain category label, see Stage 3), and `laMin`/`laIdeal`/`laMax`/`evMin`/`evMax`/`depthMin`/`depthMax`.

Those seven numbers are the **10th/50th/90th percentile of real MLB Statcast plays matching that specific result**, via a hand-built filter per result (`compute_flight_ranges.py`'s `_build_filters`) — e.g. `HR` = `events=='home_run'`; `GO`/`GORA` = `events IN (field_out, force_out) AND bb_type=='ground_ball'`; and so on for all 31 batted-ball results. `n<20`-sample results borrow an archetype-pooled fallback rather than their own too-thin sample.

**`1B`/`1BWH`/`1BWH2` filter — [Alex's correction, not yet implemented in `compute_flight_ranges.py`]:** the filter currently in the code partitions these three *exclusively* by Statcast's `launch_speed_angle` contact-quality bucket (`1B` = categories 1-4, `1BWH2` = category 5 "solid contact," `1BWH` = category 6 "barrel"), so a barrel-quality single is *only* counted toward `1BWH`, never toward `1B`'s own sample. Alex's view: this is wrong. `1B` should be the *full* population — `events=='single' AND hit_location IN (7,8,9)`, no contact-quality restriction at all — and `1BWH`/`1BWH2` should be *additional, overlapping* narrower slices of that same population (adding back `AND launch_speed_angle==6` / `==5`), not a disjoint partition of it. The reasoning: MLN's own diff-band table already independently decides whether a given play resolves to `1B` vs. `1BWH` vs. `1BWH2` (that's a Stage-1 decision, from real MLN play history) — artificially excluding well-hit balls from `1B`'s own Statcast sample just because a separate `1BWH` designation exists isn't necessary and narrows `1B`'s modeled range for no real reason. This same reconsideration likely applies to `2B`/`2BWH` too.

Given `q` from Stage 1a:
- `EV = evMin + q*(evMax-evMin)` — straight linear interpolation.
- `D = depthMin + q*(depthMax-depthMin)` — same straight linear interpolation. **[Alex's note, see below — this is one of the two things Alex thinks is most broken.]**
- **Launch angle is not a linear sweep** — it's anchored on `laIdeal` (the real median), with `q` controlling how far it deviates toward `laMin` or `laMax`: `LA = onTop ? laIdeal - (1-q)*(laIdeal-laMin) : laIdeal + (1-q)*(laMax-laIdeal)`. `onTop` (bat path above the ball → topped/lower LA, vs. below the ball → uppercut/higher LA) is the sign of the *full* pitch/swing circular delta (`signedCirc(pitch, swing, 1000)`), independent of `diff`/`q` itself. Because `laIdeal` is the median of the *same* distribution `laMin`/`laMax` are percentiles of, it structurally can't collapse onto either bound (verified: smallest margin across all 31 results is 3°, for `1BWH2`).

**One deliberate, hand-authored exception**: `depthMin`/`depthMax` for `grounder`/`infield_single`/`bunt`-family results are *not* the Statcast percentile — they're fixed real-infield-depth ranges (60-150ft / 45-90ft / 5-25ft). This is because Statcast's `hit_distance_sc` measures where a ball *first touches the ground*, which for a fly ball is the same as "where it's caught/lands" but for a ground ball is the first-bounce point, not the (much deeper) spot where an infielder fields it after the ball rolls/bounces further — confirmed against real data (shortstop-fielded groundouts, real fielding depth 147ft, showed `hit_distance_sc` medians under 15ft). This same measurement quirk is present but *not* corrected for in `1B`/`2B`/`3B`/etc., which include some ground-ball-type hits mixed in with line-drive/fly-ball ones — a live, explicit judgment call (keep the real mix of how a single actually happens) rather than an oversight, but it means the same underlying data problem is handled two different ways in two different places.

### [Alex's note] The bigger issue: `D` is computed independently of `LA` and `EV`

Right now `EV`, `LA`, and `D` are three *separately* interpolated numbers from the same `q` — nothing physically ties them together. A play can land on an `LA`/`EV` combination that describes a weak, dying humpback and *still* get a long `D`, purely because they're three independent linear reads of the same percentile ranges, not because the distance was actually derived from that launch angle and exit velocity. Alex's view: **distance (and rollout) should come out of a real trajectory physics engine that takes `LA` and `EV` as inputs**, so a play's distance is *necessarily* consistent with the speed and angle the pitch/swing numbers already produced, rather than a third independently-drawn number that merely happens to correlate via sharing the same `q`.

**A validated real-physics engine for exactly this already exists in the project and should be leveraged rather than rebuilt from scratch:** `TrajectoryCalculator-new-3D-June2026.xlsx` (project root), specifically its **`BattedBallTrajectory-1`** tab (see its `ReadMe` tab for full usage notes). This is Alan Nathan's public batted-ball trajectory calculator — the same physicist whose published optimal-launch-angle research (25-30°) was used earlier to source `laIdeal`. Key facts about it, extracted directly from the workbook:

- **Inputs** (the "orange" cells): exit speed (mph), launch angle (deg), direction (deg), batter hand (R/L), plus ball mass/circumference and atmospheric conditions (temperature, elevation, wind, humidity, barometric pressure) which can be left at sensible defaults.
- Given just exit speed + launch angle + direction + hand, **it derives backspin and sidespin automatically** (a separate `BattedBallTrajectory-2` tab exists for supplying spin manually instead, not needed here).
- **Outputs** (the "green" cells): full trajectory (x, y, z, t), with landing point, hang time, and total distance all extrapolated to field level (z=0) — i.e. exactly the two numbers (`distance`, `hangMs`) this pipeline needs, computed *jointly and consistently* from the same LA/EV input, not as two independently-drawn percentiles.
- The physics is a real drag-**and-lift** (Magnus effect / backspin) model, with coefficients "optimized using Statcast data" (`cd0=0.3008`, `cdspin=0.0292`, `cl0=0.583`, `cl1=2.333`, `cl2=1.12`, on the `BattedBallTrajectory-1` tab). This matters: a simpler drag-only simulation (no spin/lift term) was tried earlier this session as a sanity check and got the optimal launch angle *wrong* (predicted ~40-45° instead of the real ~25-30°) precisely because it omitted lift — this spreadsheet's model doesn't have that gap.
- Coordinate/angle convention is **different from the app's own**: origin at the front corner of home plate, direction 0°=straight at 2nd base, +45°=1B line, -45°=3B line (vs. `docs/js/app.js`'s `landingPoint`, which uses 0-90° with 45°=straightaway). Any port needs an explicit angle-convention mapping, not just a formula copy.
- This is an interactive Excel workbook (manual orange-in/green-out usage) — for an automated pipeline, the realistic path is almost certainly to **extract the coefficients and reimplement the same drag+lift trajectory integration natively** (Python for any offline data generation, JS if it needs to run live in the browser), not to drive Excel programmatically at runtime. The `Tables` tab likely has the full coefficient set if more than the six above are needed; the `Elevations` tab has real per-MLB-stadium elevations, which ties back into the still-open "should we filter Statcast pulls to symmetric-ish parks" question from an earlier conversation.

## Stage 3: reconciling distance with which fielder is actually there

This is where Stage 1's spray angle and Stage 2's distance, computed *independently of each other*, get reconciled against where real fielders stand — and where most of today's bugs lived, and where Alex thinks the redesign's second big idea belongs.

- **`HZ_FIELDER_BY_ANGLE`**: a fixed lookup from the 11 possible HZ angles to one of 5 infield positions (3B/SS/P/2B/1B) — angle-only, no depth information.
- **`INFIELDER_DEPTH_FT`**: real depths for those 5 positions (P=60, 1B=111, 3B=119, SS=147, 2B=147).
- **`applyGroundBallFielderDepth(m, flight)`**: runs immediately after `flightParams` returns, for `GROUND_ARCHETYPES` (`grounder`/`bunt`/`infield_single`) outs only. If Stage 2's `D` exceeds the real depth for the fielder `HZ_FIELDER_BY_ANGLE` assigned, `D` gets forcibly reduced to that exact depth. If `D` is already shorter, it's left alone (an intentionally-short "charged in on a weak roller" out).
- **`groundBallRolloutFt(m, flight)`**: computes additional roll-out distance past `D`, for *any* ball still in play (not just grounders). For a ground-ball out specifically, this was patched today: it now scales as `rolloutFraction(ev, la) * (depth - flight.distance)` — proportional to the actual remaining gap to the assigned fielder's real depth — instead of the original flat `rolloutFraction(ev, la) * ROLLOUT_FT` (a 34ft constant regardless of which fielder or how deep they play, which could never bridge an 80+ft gap for a modest ball assigned to a deep position). **[Alex's note] This whole rollout system needs reconsidering again once distance comes from the real trajectory engine above — a physics-derived distance/hang-time pair should get a physics-derived rollout too (e.g. residual ground speed at landing, from the same trajectory calculation), not a separately-patched heuristic bolted on afterward.**
- **`rolloutFraction(ev, la)`** itself normalizes EV/LA against *fixed, global* constants (`ROLLOUT_EV_LOW/HIGH = 40/115`, `ROLLOUT_LA_LOW/HIGH = -15/50`) — not any given result's own `evMin`/`evMax`/`laMin`/`laMax`. This is a leftover from before results had their own per-result ranges at all; it's the one place in the whole pipeline that's still archetype/result-agnostic in that way.
- **Outfield fielder assignment is a completely separate mechanism**: `nearestFielder(x, y)` does a plain nearest-anchor match against all 9 `FIELDER_ANCHORS_FT` positions by raw 2D distance from the computed landing point — no angle-bucket lookup, no depth reconciliation step analogous to `applyGroundBallFielderDepth`. Two different fielder-assignment strategies coexist depending on whether the archetype is ground-touching or not.
- **`applyPositionOverride(m, flight)`**: a third mechanism, keyed off `import_BRC.csv`'s optional `ExcludedPositions`/`DefaultPosition` columns for a given situation — snaps `flight` straight to a named position's anchor, skipping both of the above when it fires.

### [Alex's note] A cleaner way to think about HZ-to-fielder validity

The whole point of assigning an HZ angle to an infielder (`HZ_FIELDER_BY_ANGLE`) is to answer "which fielder would actually field this." Alex's proposal: once that fielder is determined from HZ, **cross-check it against `import_BRC.csv`'s own `DefaultPosition`/`ExcludedPositions` columns for this specific situation** (those columns already encode, per real `(result, obc, outs)` situation, which fielder(s) the play's mechanics actually require — e.g. a specific double-play's real assist chain). If the HZ-derived fielder is consistent with what `import_BRC` says for this situation, keep it as-is. If it isn't (HZ says "SS" but this situation's `DefaultPosition` requires "2B"), **override the HZ angle itself** — not just snap straight to the fielder's anchor point the way `applyPositionOverride` does today, which throws away angle-consistency entirely. Proposed simplification for the override value: use the *minimum* angle in `HZ_FIELDER_BY_ANGLE` that already maps to the required position (e.g. `3B` has `{5, 13}` → override to `5`) rather than trying to pick a "smarter" angle within that fielder's range. Critically, **the original LA/EV from Stage 2 (i.e., from the pitch/swing/`q` derivation) should NOT change** when this override fires — only the direction changes; the resulting distance/rollout should still come from the same physics (once Stage 2 has one) applied consistently to that corrected HZ, not from a separate, disconnected "snap to anchor" shortcut.

## Why this keeps needing patches — the pattern, named plainly

- **The pipeline computes "how far did it go" before "who's standing there."** Stage 2 produces a distance from a result-wide percentile range with no idea which specific fielder (60ft to 147ft away, for infielders alone) will end up assigned. Stage 3 then has to *reconcile* that number after the fact — cap it down (`applyGroundBallFielderDepth`) or stretch it out (`groundBallRolloutFt`) — rather than the fielder assignment and the distance being computed together in the first place. Every fielder-related bug found today was a consequence of this ordering, not of any single formula being "wrong" in isolation.
- **Distance is not physically derived from launch angle and exit velocity at all** — it's a third, independently-interpolated number that merely shares the same `q`. See Alex's note under Stage 2 and the `TrajectoryCalculator` workbook already in the project as the intended fix.
- **Different axes of the same problem have gotten inconsistent amounts of real-data treatment.** LA/EV are now genuinely per-result, real-median-anchored, Statcast-derived. Depth is per-result *except* where it silently isn't (the grounder-family override, and arguably the `1B`/`2B`/`3B` contact-quality partitioning Alex flagged above). HZ/spray direction is not per-result at all — one universal 5-85° formula for every result, despite the two things it's supposed to interact with (which fielder, and whether that spray pattern is even realistic for this result) both varying enormously by result in reality.
- **The rollout system was fixed by proportional patch, not by re-derivation.** Today's rollout fix (scale toward the real fielder's depth) is a real improvement, but it was arrived at by finding where the previous flat-constant formula fell short and generalizing *that specific formula*, not by asking from scratch "given a result, a contact quality, and a specific assigned fielder, what should the ball's final resting distance actually be." `rolloutFraction`'s own global EV/LA constants are a visible seam from this: everything around it is per-result, it isn't.
- **Two coexisting fielder-assignment mechanisms** (angle-bucket lookup for infield ground balls vs. nearest-anchor matching for everything else) with no shared depth-reconciliation step for the outfield case — it's untested and unclear whether outfield distances ever get corrected against `FIELDER_ANCHORS_FT` the way infield ones do.

## What to send the redesign toward

Don't just re-verify today's individual fixes (that already happened in a separate review pass). Instead:
1. **Replace the independent `D = depthMin + q*(depthMax-depthMin)` interpolation with a real trajectory-physics computation of distance (and hang time, and rollout) from `LA` and `EV`**, leveraging `TrajectoryCalculator-new-3D-June2026.xlsx`'s `BattedBallTrajectory-1` model (drag + lift, Statcast-calibrated coefficients) rather than reinventing a physics model from scratch. Decide how that gets ported (native reimplementation in Python/JS vs. some other integration) and how its own `hit_distance_sc`-derived `evMin/evMax`/`laMin/laMax/laIdeal` percentiles interact with a now-derived (not looked-up) distance.
2. Fix the `1B`/`1BWH`/`1BWH2` (and likely `2B`/`2BWH`) Statcast filters to stop being mutually exclusive by contact quality — `1B` should be the full outfield-single population, `1BWH`/`1BWH2` an additional overlapping "was this also a barrel/solid-contact" slice of it, per Alex's note above.
3. Build the HZ-to-fielder validity check against `import_BRC.csv`'s `DefaultPosition`/`ExcludedPositions`, with the minimum-angle-for-position override, replacing `applyPositionOverride`'s current blunt "snap straight to the anchor" behavior — while keeping the original LA/EV intact through that override.
4. Decide whether HZ/spray angle should get its own per-result, real-data treatment the way LA/EV already have (real Statcast `hit_location`/spray angle by result — scoped in an earlier conversation, never built).
5. Reconcile `rolloutFraction`'s global constants with wherever rollout ends up living once it's driven by real trajectory physics.
6. Unify (or explicitly justify not unifying) the two fielder-assignment mechanisms (infield angle-bucket vs. outfield nearest-anchor) — and confirm whether outfield distances ever get a depth-reconciliation step at all today.
7. Hold the whole thing to the mission constraint at the top of this document: whatever the new pipeline looks like, it must never produce a physical story inconsistent with the result the diff-band table already decided.
